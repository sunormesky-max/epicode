SMRP

Structured Memory Response Protocol

版本: 1.0 (Final)状态: 已实现分类: 记忆系统响应协议（实现无关）
规范者: Epicode本版本日期: 2026-06-19
本页: https://epicode.cn/api/v1/smrp

本规范定义 SMRP（Structured Memory Response Protocol，结构化记忆响应协议）， 一种用于智能体记忆系统的响应结构契约。SMRP 要求实现者返回的记忆单元携带三种类元信息： 角色（role）、来路（provenance）与 拓扑位置（topology），使得消费者能够区分结果的主次、解释结果的相关性来源， 并感知记忆在其所属结构中的位置。

1. 概述

1.1 动机

当前的向量数据库与检索增强生成（RAG）系统普遍以扁平、同质的 top-k 列表作为响应： 形如 [{id, content, score}, …]，其中每个结果地位相等、来源不明、结构无差别。 该约定存在三方面局限：

  1. 消费者无法区分结果的主次——无法判断哪些结果直接命中查询意图，哪些仅为关联扩展。
  2. 结果的相关性来源不透明——分数是纯向量相似度，还是经重要性、簇归属、时效等因素加权后的综合分，消费者无从得知。
  3. 记忆的结构性信息（所属簇、枢纽程度、几何位置）在响应阶段被丢弃。

SMRP 针对上述局限定义响应语义。其依据是一个事实：记忆系统在服务一次请求的过程中， 通常已经计算出关于"该结果为何相关"的若干副产物（by-product）——检索分数的组成、 关联扩展的来源、记忆在其簇中的位置。SMRP 要求实现者将这些副产物以结构化方式随响应返回， 而非在序列化阶段丢弃。

1.2 范围

本规范规定响应的结构，不规定以下内容：

  • 存储模型（图、文档块、向量等均可）；
  • 检索与排序算法；
  • 传输协议（见 1.3）；
  • 实现的具体内部表示。

1.3 与其他规范的关系

SMRP 是响应语义层协议，与传输层正交。它可承载于 JSON-RPC（例如 MCP）、 REST 或 gRPC 之上。本规范不规定传输方式，仅规定返回的记忆单元必须具备的结构。

2. 一致性

本规范中的关键词 MUST、MUST NOT、 SHOULD、SHOULD NOT、MAY 按 RFC 2119 解释。

"实现者"（Implementer）指提供 SMRP 兼容记忆后端的系统；"消费者"（Consumer）指解析 SMRP 响应的智能体或应用。 满足第 9 节所定义的某一一致性等级的实现，MAY 声称该等级的兼容性。

3. 术语

实现者（Implementer）
提供 SMRP 兼容记忆后端的系统。
消费者（Consumer）
解析并消费 SMRP 响应的智能体或应用程序。
MemoryItem
响应中一条记忆的标准化结构（见第 5 节）。
tier
记忆在本次响应中所扮演的角色（见 5.1）。
source
记忆被纳入响应的检索来源，即来路或 provenance（见 5.2）。
topology
记忆在后端结构中的位置信息，如所属簇与枢纽程度（见 5.3）。
Envelope（信封）
响应外层的 protocol、data、status 三段结构（见第 4 节）。
副产物（by-product）
实现者在服务一次请求时已计算、且本规范要求其随响应返回的信息。

4. 响应信封

每个 SMRP 响应 MUST 是一个信封对象，包含三段：

{
  "protocol": { "schema_version": "1.0", "tool": "<工具名>", "ok": <bool>, "error": <object|null> },
  "data":     { /* 工具特定负载，见第 7 节 */ },
  "status":   { "identity": {…}, "space": { "memories": <int>, "energy": <number> } }
}

4.1 protocol 段

MUST 包含 schema_version（语义化版本字符串）、tool （产生该响应的工具名）、ok（布尔值）、error（失败时为 {code, message}， 成功时为 null）。消费者 SHOULD 首先读取 ok 字段。

4.2 data 段

MUST 至少包含一个结果集合或状态字段。结构由第 7 节各工具契约规定。

4.3 status 段

SHOULD 包含 identity（后端身份胶囊）与 space （轻量空间状态，如记忆总数与可用能量）。status 为 SHOULD 而非 MUST：高频检索路径可省略以减小响应体积；变更与管理类工具 SHOULD 附带。

5. MemoryItem 结构

凡返回记忆条目之处，MUST 使用 MemoryItem 结构（可按工具语义取字段子集， 但字段名与语义 MUST 一致）：

{
  "id": "714",
  "content": "…",
  "labels": ["documentation", "architecture"],
  "timestamp": 1781840244,
  "tier": "primary",
  "source": ["vector", "kg"],
  "similarity": 0.87,
  "metrics":   { "importance": 1.9, "mass": 1.05, "memory_type": "security", "valid": true },
  "topology":  { "cluster_id": 12, "cluster_size": 68, "is_hub": false }
}

5.1 tier（角色）

每个 MemoryItem MUST 标注 tier。tier 的取值来自实现者已计算的检索信号， 其赋值过程 MUST NOT 引入新的运行时推理。取值定义如下：

primary
直接命中查询意图的高置信结果（如向量相似度直接命中）。
contextual
经关联扩展（知识图谱、共现、结构）纳入，语义相关但非直接命中。
experiential
由调用方历史交互产生、且语义关联较弱的记录（运维日志、反馈、曾发生的事件）。 其判定采用启发式：弱语义关联且来源为历史交互类标签。
hub
同时被直接命中与关联扩展命中的记忆，通常为知识结构的承重节点。
注：实现可将已有的检索信号映射为 tier。例如 Epicode 将召回阶段的二元组 [direct_similarity, association_similarity] 映射为： direct > 0 且 association = 0 → primary；association > 0 且 direct = 0 → contextual； 二者均 > 0 → hub；满足 experiential 启发式者 → experiential。

5.2 source（来路 / Provenance）

source MUST 为数组，标注该记忆被纳入响应的来源；多来源时取多值。 允许的取值：

vector
向量相似度检索命中。
kg
知识图谱关联扩展命中。
label
标签精确匹配。
temporal
时间近邻或时序命中。
rerank
重排模型调整后的命中。
reasoning
推理或类比引擎产出的命中。
hybrid
多信号融合，无法归入单一来源。

5.3 topology（拓扑位置）

topology 为扩展点。SHOULD 提供 cluster_id、 cluster_size 与 is_hub。实现特有信息（如几何层、坐标）MAY 作为额外子字段加入，但不得替换上述标准字段。

5.4 metrics（记忆自身指标）

SHOULD 提供 importance、mass、 memory_type、valid。字段名固定；不具备相应概念的实现可省略， 但 MUST NOT 改用别名。

6. 分数可解释性

当响应包含排序分数时，实现 SHOULD 提供分数组成，使消费者能够解释分数的来源：

"score_notes": {
  "base": "vector_similarity",
  "adjustments": [
    { "kind": "cluster_boost",      "delta": 0.08 },
    { "kind": "importance_boost",   "delta": 0.06 },
    { "kind": "outdated_penalty",   "delta": -0.30 }
  ]
}

7. 工具契约

本节规定各工具 data 段的结构。下列工具为典型分类；实现可按需要提供等价工具。

7.1 检索类工具

检索类工具 MUST 返回分层视图 tiers（按 tier 分桶的 MemoryItem 集合）， SHOULD 同时保留扁平的 results 以兼容既有消费者。

示例（memory_search）：

"data": {
  "query": "…",
  "tiers":  { "primary": [MemoryItem], "contextual": [], "experiential": [], "hub": [] },
  "results": [MemoryItem],
  "count": 2, "total_found": 2, "offset": 0
}

7.2 变更类工具

变更类工具（创建、更新、删除）MUST 在响应中返回所产生或受影响的副产物。 对创建操作，SHOULD 返回 placement，使消费者获知新记忆的结构位置：

"data": {
  "status": "created",
  "id": 715,
  "intake":        { "importance": 1.9, "memory_type": "security" },
  "classification":{ "auto_labels": ["ops"], "classified": true },
  "placement": {
    "layer": "service", "core": [1.5, 0.0, 6.8],
    "joined_cluster": { "id": 0, "size": 1 },
    "vertices_shared": 1, "is_seed": true, "has_port": true
  },
  "dedup":             { "checked": true, "matched_existing": null, "conflicts_marked": [] },
  "relations_formed":  22
}

更新与删除操作 SHOULD 返回 side_effects，描述对结构的影响 （如受影响的簇、释放的资源、移除的关系数）。

7.3 状态类工具

状态类工具（如 space_stats）SHOULD 返回 capacity（资源占用）与 cluster_distribution（簇规模分布）等可观测指标。 capacity 为扩展点：不同后端填入各自有意义的资源（如 Epicode 填入 Port 占用）。

8. 版本与治理

8.1 版本号

schema_version 采用 MAJOR.MINOR：

  • MAJOR：破坏性变更（移除字段、改变语义）。消费者 MUST 校验。
  • MINOR：附加性变更（新增字段、新增 tier/source 取值）。消费者 MUST 忽略未知字段。

8.2 弃用

字段弃用流程：标记 deprecated → 保留至少一个 MAJOR 周期 → 在下一 MAJOR 版本移除。

8.3 性能约束（规范性）

实现 MUST 保证：满足本规范所需的全部信息，要么是请求处理流水线的既有副产物， 要么是进程内的内存查询；MUST NOT 为产生协议字段而引入新的锁获取或同步磁盘 I/O。 若某副产物无法以零额外开销提供，实现 MAY 省略对应字段， 但 MUST NOT 编造其值。

9. 一致性等级

SMRP-Core
满足：信封（第 4 节）、MemoryItem.tier（5.1）、source（5.2）、创建操作的安置副产物（7.2）。 所有 MUST 字段为硬性要求。
SMRP-Full
在 Core 之上，额外提供 topology、metrics、score_notes 及全部 SHOULD 字段。

消费者可声明所需等级；实现据此提供保证。

10. 设计依据

本规范之所以采用固定的结构契约，而非由调度器在运行时逐条"解释"每条结果的来路，基于并发方面的考虑。 逐条解释要求为每条记忆进行来源判定；若该判定触及共享状态（知识图谱、空间索引或推理模型）， 在高并发下将引入锁竞争，其代价随并发度与结果数量之积增长。

分层分桶则不同：检索信号在请求处理流水线中已经产生，将其映射为 tier 属于进程内的确定映射， 复杂度与每条记忆成正比且无锁。固定结构契约因此能够同时满足"可解释"与"高并发"两项要求， 而运行时解释通常只能满足其一。

11. 安全考量

  • 响应 MUST NOT 包含凭证或密钥。
  • topology 字段 SHOULD NOT 暴露可被用于侧信道攻击的内部物理地址或实现细节。
  • 实现 SHOULD 对消费者可见的字段进行最小化裁剪。

experiential 是否独立
独立，采用启发式判定。理由：须区分"所知"与"所经历"，后者与身份相关。
source 取值集合
纳入 rerank 与 reasoning，因其可信度性质与直接检索不同。
安置字段命名
创建操作使用 placement，更新与删除使用 side_effects，因语义不同。
流式响应
1.0 版本不纳入，留待后续版本。
